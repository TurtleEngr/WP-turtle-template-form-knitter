*** Why it can't just drop the requires
- The requires load =wp_generate_attachment_metadata()=, which makes the thumbnail and medium sizes.
- WordPress only loads that function for admin requests. A CF7 submission is a front-end REST request, so the function isn't there.
- So the work has to move to a request where WordPress has already loaded it.

*** What the new code does
- =ttfk_fCreateAttachment= still copies the file and adds it to the
  Media Library. Instead of making the image sizes, it marks the
  attachment with a meta key, =_ttfk_need_meta=.
- A new function, =ttfk_fMakeAttachMeta=, runs on =admin_init=. It
  makes the sizes for up to 10 marked attachments and removes each
  mark.
- =admin_init= fires on any admin page load, including
  =admin-ajax.php=. In practice the sizes exist before anyone reviews
  the pending post.

*** Test results
- Right after the submission, the pending post was created and the
  image was attached and set as the featured image. It had no image
  sizes yet.
- After one request to =admin-ajax.php=, the 150×150 and 300×200 sizes
  were on disk and the metadata was saved.
- No PHP errors were logged.

*** Tradeoffs
- Until an admin page is loaded, the image has no smaller sizes. The
  post is Pending, so it isn't public in that window.
- =ttfk_fCreateAttachment= now returns the attachment ID instead of
  the metadata. Nothing in the plugin uses the return value.

*** Short answer:

not a real problem here, and yes, it can be cleared.

The warning comes from one place, =ttfk_fMakeAttachMeta()= (line ~229
in =turtle-template-form-knitter.php=):

#+begin_example
$tIdList = get_posts([
    'post_type'   => 'attachment',
    'post_status' => 'inherit',
    'meta_key'    => ttfk_cNeedMetaKey,   // <-- flagged
    'fields'      => 'ids',
    'numberposts' => 10,
]);
#+end_example

*** Why it's not really slow.

The =WordPress.DB.SlowDBQuery= sniff flags any use of =meta_key=,
=meta_value= or =meta_query=, without looking at how it's used. The
slow case is filtering on =meta_value=, which is not indexed. You only
filter on =meta_key=, which is indexed in =wp_postmeta=. The query
only fetches IDs and is limited to 10 rows. It's also a warning, not
an error, so the WordPress.org plugin review usually doesn't block on
it.

*** The one real cost.

The query runs on every =admin_init=, so every admin page load does
this join, even when nothing is pending. On a site with a big
=wp_postmeta= table that's a small, constant overhead.

*** Ways to fix it:

1. Suppress it with a reason.

   This is the smallest change and the usual practice:

#+begin_example
   // phpcs:ignore WordPress.DB.SlowDBQuery.slow_db_query_meta_key -- indexed key only, max 10 IDs
   'meta_key'    => ttfk_cNeedMetaKey,
#+end_example

   It changes no behavior. The admin_init cost stays.

2. Gate it with an option flag.

   When =ttfk_fCreateAttachment()= adds the meta, also set an
   autoloaded option such as =ttfk_need_meta =
   1=. =ttfk_fMakeAttachMeta()= returns at once unless that flag is
   set, and clears the flag when the query finds nothing. This removes
   the per-page cost. You would still need option 1's comment to make
   the warning go away.

3. Replace the post meta with an option that holds the list of pending IDs.

   This removes the meta query entirely, so the warning disappears
   with no ignore comment. The tradeoff is that two form submissions
   arriving at the same moment could both read and rewrite the list,
   and one ID could be lost. That would leave an attachment without
   thumbnails. The current per-post meta approach doesn't have that
   race.

My suggestion is 1., or 1. + 2. if you want to drop the admin
overhead. Option 3 trades a harmless warning for a small correctness
risk.
